## 2. 证据等级合同

所有 QA 文档、问题状态和发布结论必须使用以下等级，不得跨级推断：

| 等级 | 证据类型 | 可以证明 | 不能证明 |
|---|---|---|---|
| E0 | 静态文件、注册表、配置检查 | 内容被声明、资源可加载 | 内容可玩或体验正常 |
| E1 | 纯策略、生成器、离线数据扫描 | 规则确定性、地图特征可能存在 | 玩家能够正常到达、碰撞正确、视觉合理 |
| E2 | 真实运行时中的服务、状态或事务 | 服务可工作、状态可保存 | 玩家通过正式输入完成了流程 |
| E3 | 生产场景 + 正式输入 + 真实物理/UI/交互 | 玩家可在被覆盖路径实际操作并完成断言 | 未覆盖内容、完整视觉体验和长期主观手感 |
| E4 | 最终导出程序的桌面操作、截图/录屏和独立人工复审 | 最终包体中的可见布局、反馈、连贯性和主观体验 | 所有随机 Seed 与无限程序化空间 |

“完整探索”至少需要 E3 的区域、连续路线、边界、兴趣点和特殊环境覆盖，并对关键视觉与手感提供 E4 证据。单独的 E0/E1/E2 不得标记为完整探索；production-scene desktop acceptance 也不得被冒充为最终导出程序人工 E4。

## 3. 本轮发现的真实问题

### 3.1 精确服务失败原因被通用 UI 文案覆盖

旧 `FurnacePanel` 在点击背包或机器槽位时存在两条同步反馈路径：

1. `FurnaceService` 在失败时立即发出 `transfer_rejected(machine_id, reason)`，提供 `unsupported_item`、`inventory_full` 等精确原因；
2. 面板的点击处理函数在调用返回 `false` 后，又无条件写入通用文案“该物品不能投入”或“槽位为空，或背包没有足够空间”。

结果是生产服务已经给出的精确原因会被第二条路径覆盖。玩家无法区分“不支持的物品”“槽位不匹配”“背包已满”等不同问题，自动化也无法可靠审计真实失败原因。

本轮没有删除服务 signal，也没有把断言改成只看“出现过任意错误”。修复方式是：

- `item_transferred`、`item_smelted`、`transfer_rejected` 成为生产成功/失败反馈的权威来源；
- 面板记录 `_feedback_revision`；
- 只有服务没有发出任何精确结果时，点击处理函数才显示通用 fallback；
- `inventory_full` 明确显示“背包空间不足，产出仍安全保留在熔炉中”；
- visual snapshot 同时公开 `status_kind`、`status_reason`、`status_target_id` 和实际文案。

### 3.2 旧熔炉桌面证据没有形成跨会话闭环

旧旅程存在以下证据缺口：

- 通过直接 `block_interaction.interact()` 打开熔炉，绕过玩家中心射线和真实右键；
- 机器槽位和玩家背包控件没有稳定身份，测试容易依赖控件顺序；
- 只验证投入、加工、取出和保存文件字段；
- 没有满背包真实鼠标失败；
- 没有返回菜单后清除调度器和运行时机器记录；
- 没有完整重新组合生产场景；
- 没有验证待取产物只恢复一次；
- 没有验证历史 `item_smelted` 事件不会在重载后重放；
- 没有在取出产物后再次保存并第二次重载，无法排除重复产物或原料/燃料复活。

这些缺口使旧证据最多属于 E3 局部 + 保存检查，不能写成完整机器闭环。

## 4. 本轮完成的产品与架构改进

### 4.1 稳定的机器与背包控件身份

熔炉面板现在为正式控件公开：

- 玩家背包：`inventory:<slot_index>`；
- 原料槽：`furnace-slot:input`；
- 燃料槽：`furnace-slot:fuel`；
- 产出槽：`furnace-slot:output`；
- 机器身份：由正式世界坐标机器 ID 解析；
- 每个控件同时公开方向、槽位名称和索引。

自动化、可访问性和未来本地化不再依赖中文按钮文本或控件排列顺序。

### 4.2 可审计的熔炉 visual snapshot

`FurnacePanel.get_visual_snapshot()` 现在能够返回：

- 当前机器 ID；
- 当前状态种类、精确原因、目标身份和玩家文案；
- 当前配方、进度和燃料比例；
- 原料、燃料、产出三个槽位的稳定身份、物品、数量和禁用状态；
- 玩家背包全部控件的稳定身份、槽位索引、物品、数量和 tooltip。

该接口只暴露可观察状态，不绕过生产服务执行操作。
