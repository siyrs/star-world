## 2. 证据等级合同

所有 QA 文档、问题状态和发布结论必须使用以下等级，不得跨级推断：

| 等级 | 证据类型 | 可以证明 | 不能证明 |
|---|---|---|---|
| E0 | 静态文件、注册表、配置检查 | 内容被声明、资源可加载 | 内容可玩或体验正常 |
| E1 | 纯策略、生成器、离线数据扫描 | 规则确定性、地图特征可能存在 | 玩家能够正常到达、碰撞正确、视觉合理 |
| E2 | 真实运行时中的服务、状态或事务 | 服务可工作、状态可保存 | 玩家通过正式输入完成了流程 |
| E3 | 生产场景 + 正式输入 + 真实物理/UI/交互 | 玩家可在被覆盖路径实际操作并完成断言 | 未覆盖内容、完整视觉体验和长期主观手感 |
| E4 | 最终导出程序的桌面操作、截图/录屏和独立人工复审 | 最终包体中的可见布局、反馈、连贯性和主观体验 | 所有随机 Seed 与无限程序化空间 |

“完整探索”至少需要 E3 的区域、连续路线、边界、兴趣点和特殊环境覆盖，并对关键视觉与手感提供 E4 证据。单独的 E0/E1/E2 不得标记为完整探索；production-scene desktop acceptance 也不得被冒充为最终导出程序人工 E4。

## 3. 本轮发现并修复的真实问题

### 3.1 切石机精确失败原因被通用 UI 文案覆盖

旧 `StonecutterPanel` 与熔炉旧实现存在同源缺陷：

1. `StonecutterService` 在失败时立即发出 `transfer_rejected(machine_id, reason)`，可以提供 `unsupported_item`、`unsupported_input`、`slot_full_or_mismatch`、`inventory_full` 等精确原因；
2. 面板点击处理函数在调用返回 `false` 后，又无条件写入“该物品不能切割”或“槽位为空，或背包没有足够空间”等通用文案。

生产服务给出的精确原因因此被第二条同步路径覆盖。玩家无法区分不支持物品、槽位冲突和背包已满，自动化也无法审计失败对应的是哪个真实按钮。

本轮修复为：

- `item_transferred`、`item_processed`、`transfer_rejected` 成为生产成功/失败反馈的权威来源；
- 面板使用 `_feedback_revision` 判断服务是否已经发出结果；
- 只有服务没有产生精确结果时才显示通用 fallback；
- `_pending_action_target_id` 把本次点击的 `inventory:*` 或 `stonecutter-slot:*` 身份带入同步拒绝快照；
- `inventory_full` 明确显示“背包空间不足，切割产出仍安全保留在机器中”；
- visual snapshot 同时公开 `status_kind`、`status_reason`、`status_target_id` 和玩家实际看到的文案。

### 3.2 旧切石机桌面旅程没有证明待取产物和 Chunk 生命周期守恒

旧旅程已经有真实世界、右键、鼠标、共享调度和一次保存/重载，因此不是无价值测试；但它在加工后立即取回石台阶，无法证明：

- 满背包失败时机器产物是否完整保留；
- 保存文件是否精确保留待取产物；
- 返回菜单后运行时机器记录是否清空；
- 完整重载后待取产物是否只恢复一次；
- 机器所在 Chunk 卸载后，权威机器状态是否被错误删除；
- Chunk 重新加载后，真实方块与机器状态是否能够重新组合；
- 相邻熔炉状态是否会被切石机卸载或取回操作串改；
- 取回产物后再次保存和重载是否会重复石台阶或复活原石；
- 历史 `item_processed` 和玩家汇总事件是否会在重载时重放。

旧证据因此只能标记为 E3 较强，而不能标记为完整玩家闭环。

### 3.3 新静态门禁首次运行暴露 PowerShell 插值缺陷

首版 `validate_stonecutter_closed_loop.ps1` 的错误信息使用：

```powershell
$count:
```

PowerShell 将冒号与变量名一起解析，导致静态门禁在执行合同之前发生 ParserError。该问题是新测试基础设施缺陷，不是游戏逻辑缺陷。

修复为：

```powershell
${count}:
```

修复后静态合同、严格 Godot 导入、切石机领域和全部相邻回归均正常执行并通过。该经历也证明门禁本身必须被真实运行，不能只凭 YAML 或脚本文本存在就宣称有效。

### 4.4 Chunk 证据边界

本轮确实触发并验证了 production world 的真实 Chunk 卸载和重新加载，而不是只读取一个伪造状态字段。但触发方式是测试将 streaming focus 移到卸载半径之外，然后返回玩家位置；它不是玩家从出生点连续走到远处再走回来的路线旅程。

因此本轮能够证明：

- Chunk 可见性生命周期不会删除权威机器状态；
- 重新加载 Chunk 时真实方块和机器状态可以重新组合；
- 卸载一个机器 Chunk 不会串改相邻机器领域。

它不能证明：

- 五张地图的正常玩家路线全部连通；
- 多台切石机跨多个 Chunk 长时并发没有体验问题；
- 玩家连续移动导致的全部流式边界、空气墙和卡位问题均不存在。

## 7. 性能和外部工具证据边界

GitHub Actions 桌面与性能采集环境使用：

- Windows Server 2025；
- Godot 4.7；
- `gl_compatibility`；
- ANGLE；
- `Microsoft Basic Render Driver`；
- dummy audio driver。

因此该环境可以证明：

- 构建、导出、启动和自动化链路可运行；
- schema、数据一致性、缓存遥测和外部内存采样正确；
- 被覆盖旅程没有 crash、fatal、parse error 或测试出口泄漏；
- UI 截图能够生成并接受结构化复审。

它不能证明最低或推荐玩家 GPU 的 FPS 达标，软件渲染 Runner 的 FPS 不得用于产品宣传。

此外，当前外部 GUI 工具对 fresh EXE 的窗口激活和输入捕获存在权限阻塞。项目采用 production-scene desktop InputEvent 完成 E3 自动化，但不能把它标记为最终导出程序的 E4 人工操作。该边界继续由 `BLOCKER-GUI-001` 和 `BLOCKER-PERF-CI-001` 记录。

## 8. 剩余工作的优先顺序

下一阶段继续按照“一个关键领域一个真实玩家闭环”的方式推进，不再用服务存在性代替玩家体验：

1. 畜牧/繁殖：父母、幼崽、冷却、死亡/卸载和完整活体重载；
2. 牧场产物：跨会话产蛋计时、满背包拾取失败、多动物和长期产出压力；
3. 农业：从空背包获取材料到锄地、播种、灌溉/施肥、成长、收获和重载；
4. 床与重生：玩家放床、设置出生、保存、死亡、返回菜单、重载和回床；
5. 探索/里程碑：正常寻找材料、制作仪器、到达地点、失败地图反馈和全部里程碑；
6. 五图连续路线：出生点到关键区域、边界、狭窄区、水下、地下、高空和脱困；
7. 多机器长时：多台熔炉/切石机跨多个实际玩家路线 Chunk 的并发、异常退出和离线边界；
8. 最终导出 E4：真实 Windows 包体中的完整操作、截图/录屏和独立人工体验；
9. 真实目标硬件：最低/推荐配置的同场景性能与严格 120 分钟长稳。
