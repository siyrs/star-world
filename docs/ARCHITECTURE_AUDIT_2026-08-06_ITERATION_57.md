# Architecture Audit · 2026-08-06 · Iteration 57

## 审计范围

复审 Iteration 56 五项优先级、PR #102 的实际差异、战斗伤害链、Encounter 强度边界、Reward Economy、长期运行有界性和发布证据诚实性。

## 发现 1：PR 描述与实际 Git 差异不一致

PR #102 最初描述了完整战斗迭代，但实际只提交了临时仓库快照 workflow。描述不能替代代码、测试或 CI。

决策：拒绝空壳合并；在同一迭代分支补齐实现、永久门禁和闭环报告，并删除临时快照 workflow。

## 发现 2：受击反馈缺少统一来源上下文

旧链路能结算伤害，但 HUD 无法可靠区分前后左右，也不能确认近战、深渊弹或环境来源。若 HUD 自行查找攻击者，会引入全图扫描、时序竞态和重复伤害逻辑。

决策：由攻击者在权威伤害调用中提供 source position；玩家在同一结算中计算方向；CombatService 合并上下文并发布一个 `incoming_damage_resolved` 结果。HUD 只渲染最终伤害、护甲吸收、方向与来源。

## 发现 3：反馈必须有固定瞬态容量

每次受击动态创建边缘控件会在混战和长稳中形成节点增长。

决策：HUD 初始化一次前、右、后、左固定四槽池，只更新剩余显示时间。关闭视觉脉冲不关闭可访问文字。

## 发现 4：遭遇难度不能污染世界存档

直接修改 Encounter profile 或保存活动压力会改变正式敌人配置和存档语义。

决策：versioned 强度 profile 只提供冷却与危险压力倍率；正式 Encounter ID、成员编组、奖励、世界进度和存档 schema 均不变。损坏设置回退到标准。

## 发现 5：旧奖励成品弹药会形成无限农场

Iteration 56 的奖励仍直接提供完成弹药。高效率玩法可能把低风险 Encounter 变成弹药生成器，而且“深层地图增加火药占比”的路线图无法真正成立。

决策：正式奖励只允许燧石和火药；注册表与运行时事务双层拒绝成品弹药；箭矢配方正式使用燧石，形成奖励输入到制造输出的闭环。

## 发现 6：注册表验证不足以防运行时旧数据

即使新 JSON 严格有效，旧 pending、测试注入或未来错误调用仍可能把完成弹药送入事务。

决策：在首次发放、pending 重试、奖励提交与 additions 构造四个运行时边界重复过滤。异常记录进入 rejection diagnostics，不部分写入 Inventory。

## 发现 7：长稳必须区分逻辑证明与硬件资格

每个 PR 等待真实一小时不经济；但把确定性逻辑测试称为目标硬件性能证明同样不诚实。

决策：永久 CI 使用恰好 3,600 秒逻辑夹具证明状态、预算、保存重载和清理；真实最低/推荐硬件仍执行独立 7,200 秒最终包资格流程。

## 复审结论

- Iteration 56 优先级 1“掩体反制”已由 PR #94 完成；
- 优先级 2–5 在 Iteration 57 完成工程实现与自动化门禁；
- 没有新增第二份伤害、Encounter、Inventory、Crafting 或 Save 系统；
- 固定容量、原子事务和世界生命周期边界继续成立；
- 自动化完成不解除 E4-H 与目标硬件 **HOLD**。
