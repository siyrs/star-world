# Architecture Audit · 2026-07-30 · Iteration 55

## 审计目标

在玩家枪械、敌对投射物和深渊射手稳定后，继续推进多敌种协同遭遇，同时避免简单提高刷怪数量带来的不可控压力。

## 发现 1：刷怪仍是单物种随机抽取

`CreatureSpawner` 每个周期只选择一个物种。虽然僵尸、射手和重击者都能独立运行，但无法保证它们形成前卫、远程和终结者的角色组合。

决策：新增独立 Encounter Director，通过数据 profile 一次规划完整小队，Spawner 仍是唯一创建入口。

## 发现 2：只有数量上限，没有总危险预算

五只普通僵尸和两只射手、一只重击者并不等价。仅按数量上限无法表达真实压力。

决策：每个 profile 同时约束现有压力、遭遇压力和最大总压力；正式上限为 8.0。

## 发现 3：组合创建可能公开半套小队

如果连续创建四名成员时第三名失败，前两名若继续存在，HUD 和行为会观察到不完整遭遇。

决策：成员创建作为一个原子事务；任一失败立即回滚已经创建的成员。

## 发现 4：低血量玩家仍会继续叠加敌人

原生态刷新只关心数量和概率，不关心玩家是否已接近死亡。

决策：生命低于 35% 时全局暂停新遭遇；profile 还可配置更高阈值。该逻辑不删除现有敌人，只停止新增压力。

## 发现 5：协同不应引入全图广播

所有敌人搜索全局小队或共享黑板会扩大热路径和耦合。

决策：Director 只持有最多 12 个 WeakRef，并在创建时给成员写入瞬态 encounter ID、角色和同一本地玩家目标。

## 发现 6：遭遇状态不应进入存档

敌人位置、剩余成员和遭遇冷却都是当前运行会话的瞬态。如果进入存档，会产生半队恢复、跨版本 profile 漂移和区块未加载引用。

决策：保存结构不增加任何遭遇字段；返回菜单、世界切换和重载后从零开始。

## 发现 7：玩家缺少当前小队结构信息

同时面对近战、射手和重击者时，仅靠单个攻击提示难以理解整体局势。

决策：新增轻量 HUD，显示遭遇名称、剩余人数、危险值和角色组合；低血量降压时解释暂停原因。

## 发现 8：长期模拟不能依赖真实等待一小时

真实 Windows Release 运行仍需要覆盖，但每次领域验证不应等待 60 分钟墙钟时间。

决策：纯策略执行 3600 秒确定性模拟，同时真实桌面、Runtime Soak 和 Windows Release 验证生产组合与资源释放。

## 最终架构

```text
hostile_encounters.json
        │
        ▼
HostileEncounterRegistry  ── 原子 staged commit
        │
        ▼
HostileEncounterPolicy    ── 资格、危险预算、角色编队
        │
        ▼
HostileEncounterDirector  ── 每秒一次决策、WeakRef 追踪
        │
        ├── CreatureSpawner（唯一生物创建/清理）
        ├── CombatService（唯一伤害权威）
        └── HostileEncounterOverlay（只读 HUD）
```

## 不变量

- 不替换稳定 ServiceHub 或 CreatureSpawner 公共入口；
- 不创建第二套伤害、掉落、保存或 AI 导航系统；
- 无 Timer、线程、全图扫描；
- 单队最多 5、总追踪最多 12、活动遭遇最多 2；
- 配置失败不公开部分状态；
- 世界生命周期结束后零遭遇状态。
