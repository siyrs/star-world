# Architecture Audit · 2026-07-25 · Iteration 38

## 范围

本轮继续审计大世界数量下的主菜单体验。前序迭代已经限制 Primary 修复、完整世界读取、Sidecar 写入和瞬时目录暂存，但存档浏览器仍可能把磁盘优化后的收益消耗在 UI 节点抖动和手动刷新上。

## 发现

### 1. 每次刷新销毁并重建全部世界行

旧 `SaveBrowserPanel.refresh()` 对 `_list` 的全部子节点执行：

```text
queue_free
```

随后为每个世界重新创建：

```text
HBoxContainer
选择 Button
继续 Button
两个信号连接
```

这使 UI 节点数量和创建成本继续与世界数量线性增长。目录读取已经有界，但节点树、布局和退出清理仍然无界。

### 2. 稳态刷新也产生节点抖动

即使 100% sidecar 命中、磁盘读取已经很轻，刷新仍会销毁稳定行并重新创建完全相同的控件。节点树变化会增加布局、主题解析、信号连接和 ObjectDB 退出压力。

### 3. 目录收敛依赖手动刷新

当前 `list_worlds()` 每次只推进一个有界批次。玩家必须反复点击刷新、关闭再打开面板，目录暂存和 Sidecar 才会完全收敛。

这虽然保证单次操作安全，却把内部维护工作暴露为玩家操作负担。

### 4. 不应使用 Timer 或无限 `_process`

新增 Timer 会引入第二套调度生命周期；持续运行 `_process` 则会在目录永久失败时形成无界循环。正确做法是只在面板可见、有积压且仍有固定预算时临时启用处理。

## 决策

### 固定 24 行池

存档浏览器只创建 24 个世界行节点，并在刷新和分页时重绑定：

```text
MAX_VISIBLE_ROWS := 24
```

无论目录中有 24、72 或更多世界，节点数量保持固定。分页不调用存档服务。

### 最多 6 个自动整理轮次

一次显式刷新后，若目录诊断仍有积压，面板可见期间每帧最多执行一次后续有界扫描：

```text
MAX_AUTO_SETTLE_PASSES := 6
```

积压归零、面板隐藏或预算耗尽时立即关闭 process。没有 Timer、线程或后台持久队列。

### 可观测但不持久化

面板暴露固定大小 Snapshot，包括行池大小、页面、刷新次数和自动整理使用量。Snapshot 不进入世界存档，不包含完整 metadata 或 payload。

## 真实验收设计

### Headless

- 72 个世界形成三页；
- 行池和行创建数始终为 24；
- 页面切换不会增加 `list_worlds()` 调用；
- 可收敛积压在四个跨帧轮次后停止；
- 永久积压最多执行六个轮次并停止；
- 重复刷新不创建新行。

### 真实桌面

正式 GameScene 创建 72 个世界并删除全部目录：

- 隐藏面板先执行一次显式扫描；
- 打开面板后无需手动刷新即可完成目录整理；
- 三页访问全部世界；
- 行节点总数固定为 24；
- 页面切换不触发目录或磁盘扫描；
- 最终稳态完整读取、写入和暂存均为零；
- 输出 1280×720 截图和机器可读 JSON。

### 全量门禁

最终候选继续通过：

- 目录暂存、权威读取、目录重建、多世界恢复与 Save Recovery；
- 总 Runtime 与全部领域回归；
- 三轮 lifecycle soak；
- 完整真实桌面输入/UI 矩阵；
- Windows Release 实际导出与启动。

## 结论

本轮把世界目录的有界合同延伸到了 UI 层：磁盘工作、跨刷新状态和控件节点都不再随世界数量无界增长。玩家打开存档面板后，目录维护会在固定轮次内自动推进，同时仍保持世界全部可访问、Primary 唯一权威和可验证的真实桌面证据。
